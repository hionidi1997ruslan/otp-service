# OTP Service — спецификация

> Статус: черновик v0.1. Пункты с пометкой **[решить]** — открытые вопросы, см. раздел 9.

## 1. Назначение

Учебный (pet) сервис одноразовых кодов (OTP — One-Time Password).
Сервис выдаёт короткий цифровой код, хранит его в БД и проверяет код, который прислал клиент.
Реальной отправки кода (SMS, email) нет: код возвращается прямо в ответе, сервис работает как mock для тестирования.

Главная цель — **стенд для нагрузочного тестирования**:
- поиск максимальной производительности;
- подтверждение максимальной производительности;
- тест надёжности (длительная нагрузка).

Поэтому сервис должен быть простым и предсказуемым, а также давать метрики, по которым видно его поведение под нагрузкой.

Основной сценарий (и сценарий нагрузочного скрипта):
1. Клиент вызывает `POST /otp`.
2. Сервис генерирует код, присваивает ему `id`, сохраняет запись в БД и возвращает `id` и `code`.
3. Клиент вызывает `POST /otp/{id}/verify` с кодом.
4. Сервис находит запись в БД по `id`, сравнивает коды и отвечает «верно» или «неверно».

Попутные цели: освоить Spring Boot (REST, JPA, Postgres), тесты и метрики (Actuator, Prometheus).

## 3. Термины

- **OTP / код** — строка из 6 цифр, например `048213`.
- **Сессия OTP** — запись в БД: один выданный код с его состоянием.
- **TTL** — время жизни кода.

## 4. Функциональные требования

### FR-1. Генерация кода
- Код состоит из 6 цифр (0–9) и генерируется через `SecureRandom`. Ведущие нули допустимы.
- При каждой генерации в БД создаётся новая запись с уникальным `id` (UUID).
- Код действует **5 минут** **[решить]**.

### FR-2. Проверка кода
- Клиент передаёт `id` сессии и код.
- Проверка успешна, если одновременно выполнены условия:
  1. сессия существует;
  2. срок действия не истёк;
  3. код ещё не был использован;
  4. лимит попыток не исчерпан;
  5. код совпадает.
- После успешной проверки код помечается как использованный, повторно он не принимается.
- Неверный код увеличивает счётчик попыток. Лимит — **3 попытки** **[решить]**, после него сессия блокируется.

### FR-3. Состояния сессии

```
ACTIVE ──(верный код)──────────► USED
  │
  ├──(истёк TTL)───────────────► EXPIRED
  │
  └──(3 неверные попытки)──────► BLOCKED
```

`EXPIRED` можно не хранить в БД, а вычислять по `expiresAt` при проверке.

## 5. API

Базовый путь: `/otp`. Сейчас в коде эндпоинт называется `POST /token`, предлагается переименовать **[решить]**.

### 5.1. `POST /otp` — выдать код

Тело запроса не требуется.

Ответ `201 Created`:
```json
{
  "id": "3f2b8c1e-6a4d-4e2f-9b7a-1c2d3e4f5a6b",
  "code": "048213",
  "expiresAt": "2026-10-14T12:05:00Z"
}
```
Поле `code` есть в ответе, потому что сервис работает как mock. В настоящем сервисе код отправлялся бы по SMS или email.

### 5.2. `POST /otp/{id}/verify` — проверить код

Запрос:
```json
{ "code": "048213" }
```

| Ситуация | HTTP | Тело |
|---|---|---|
| Код верный | `200 OK` | `{"valid": true}` |
| Код неверный, попытки остались | `400 Bad Request` | `{"valid": false, "error": "INVALID_CODE", "attemptsLeft": 2}` |
| Неверный формат кода (не 6 цифр) | `400 Bad Request` | `{"valid": false, "error": "BAD_FORMAT"}` |
| Сессия не найдена | `404 Not Found` | `{"valid": false, "error": "NOT_FOUND"}` |
| Код уже использован | `409 Conflict` | `{"valid": false, "error": "ALREADY_USED"}` |
| Срок действия истёк | `410 Gone` | `{"valid": false, "error": "EXPIRED"}` |
| Попытки исчерпаны | `429 Too Many Requests` | `{"valid": false, "error": "BLOCKED"}` |

## 6. Модель данных

Таблица `otp` (сущность `OtpEntity`):

| Колонка | Тип | Ограничения | Сейчас в коде |
|---|---|---|---|
| `id` | uuid | PK | есть |
| `code` | varchar(6) | NOT NULL | есть |
| `created_at` | timestamptz | NOT NULL | нет |
| `expires_at` | timestamptz | NOT NULL | нет |
| `attempts` | int | NOT NULL, default 0 | нет |
| `status` | varchar(16) | NOT NULL: `ACTIVE` / `USED` / `BLOCKED` | нет |

## 7. Нефункциональные требования

- **Безопасность.** Сравнивать коды за постоянное время (`MessageDigest.isEqual`). Хранить код в виде хэша — опционально **[решить]**.
- **Наблюдаемость.** Открыты эндпоинты `/actuator/health` и `/actuator/prometheus`, плюс свои метрики:
  - `otp_generated_total` — сколько кодов выдано;
  - `otp_verified_total{result="success|invalid|expired|blocked|used|not_found"}`.
- **Конфигурация.** TTL, длина кода и лимит попыток задаются в `application.properties`, например `otp.ttl=5m`, `otp.length=6`, `otp.max-attempts=3`.
- **Тесты:**
  - unit-тест генератора: длина кода и только цифры;
  - unit-тесты логики проверки: все строки таблицы из 5.2;
  - интеграционный тест контроллера (`@SpringBootTest` + `MockMvc`).
- **Запуск.** Поднять БД командой `docker compose up -d`, затем запустить приложение командой `./mvnw spring-boot:run`.
